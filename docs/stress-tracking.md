# 接收滑动窗口与队列观测

接收窗口与队列观测已通过虚拟 CAN、模拟驱动和本地服务测试。真实硬件与实际 24–72 小时运行仍需独立验收。

## 冻结配置与兼容

计划及每个附加 flow 可选 `tracking: {"format":"sliding","capacity":4096}` 和 `queues: {"sample_every":100}`。省略 tracking 仍使用精确位图，显式 exact 与省略序列化一致；省略这两个选项保留原计划指纹及原报告版本。新能力使用报告与节点验证版本 **11**，协调器在 prepare/commit 前拒绝不支持的节点。附加流分别声明；Web 添加反向流时复制当前选项，自适应各子阶段继承选项。

滑动容量必须为 64..1048576 的 2 次幂；队列采样间隔必须为正整数。配置变更使 Web 预检和发送授权失效，只有重新验证后的明确开始动作可以运行。示例见 [sliding-window.json](../examples/stress/sliding-window.json)；示例文件本身不会执行发送。

## 接收窗口与历史边界

接收位图复用 capacity 个槽位。发送序号将越过活动窗口时，先结算并记录之前的发送结果，再按半窗口步长推进每个 receiver。推进和该接收器的处理/记录使用同一把短锁。淘汰时分别累计已接收 unique、计划缺失及精确已提交集合中的缺失，然后清空被复用的槽位。不同 receiver 独立推进、计数与记录；逐阶段 unique 使用有界累计数组，不能从循环位图反推历史。

报告给出 capacity、base、finalized_through、unique_retired、finalized_missing_expected、finalized_missing_submitted、late_after_window、future_outside_window 和 finalized。运行中 frozen 计数只描述已淘汰前缀；正常或中断收尾后把剩余计划范围结算，finalized_through 为整个有限计划的 count，unique_retired 为最终已接收总数。

低于 base 的迟到帧只增加 late_after_window：不补 unique、不改历史缺失、不补阶段计数、不生成计时匹配或 RTT 回复。该计数非零会阻止 pass，即使冻结的普通质量容差允许缺失。窗口前方尚未开放的帧不推动窗口，只记 future_outside_window，并使接收证据不完整。Classic pattern 的旧 checkpoint 不能重开已淘汰关联；不能关联的模式数据仍按 Classic pattern 的 unverified/ambiguous 规则处理。

容量需覆盖预期接收积压和调度延迟；半窗口推进后，边缘帧可用的剩余空间至少为半窗口。窗口小于实际积压时明确失败，不以接收迟到修复先前结论。

滑动窗口只替换 **RX 去重存储**。TX 提交位图继续精确保存；RTT 去重/匹配、计时覆盖率、Classic 关联仍按已有有界模型记账。没有本地发送水位的 responder-only RTT 拒绝滑动模式，可继续使用 exact。计划仍受有限 u32 序列、72 小时时长、256 MiB 跟踪加队列预留、2 GiB 证据预算与文件数限制；它不是无限时长或所有状态常量内存模式。多流同时合计内存与采样负载，自适应顺序子阶段按峰值预留。

## 按设备拆分控制锁

Runtime 保留一个短同步目录锁，统一分配 session/lease/acquisition 代次、检查最多八个会话、原子预留设备集合和全局压测准入。异步控制锁按后端声明的 device_id 分片；同一设备的多个通道继续串行，独立设备的 configure/start/renew/stop/prepare 不相互等待驱动调用。设备 ID 依然是后端身份声明，不是硬件认证。

创建在持有设备锁后交由 Runtime 拥有的任务完成，调用者取消不会遗留无人管理的配置；目录在配置前登记 pending claim，失败自动回滚。预留 token 在提交创建时再次核对当前注册表，过期/异源预留不得绕过设备占用。清理仍匹配原 session、租约和 acquisition epoch，不能关闭替换者。设备集合预留、同步停止门、全局 shutdown fence、单 Runtime 的总预算没有拆成多份。

聚合 list/snapshot 需要收集全部设备状态，仍可能等待慢设备；独立单设备操作不因此持有其他设备的异步控制锁。底层驱动若自己只有一个 worker，其串行限制仍然存在，Runtime 不声称消除了驱动内部排队。

## 队列观测与证据

既有 receiver.queue_high_water 记录在线观察到的全部接收积压，evidence.queue_high_water 记录证据写队列积压。新增每 receiver 的 queues 保存 eligible RX 采样数、observed_high_water、固定 25 桶的 residence 分布及 invalid_timestamps。eligible 指匹配本计划 tag 的帧，或 Classic pattern 选定的 ID。每 sample_every 个 eligible RX 采样一次，从 ordinal 0 开始；重复和载荷错误的匹配帧仍参与队列观测。

深度是取出当前事件后可见的队列长度加一，可能包含其他流/无关帧；采样高水位是实际峰值的下界。驻留为 backend.received_at 到接收校验开始的同机单调时间，包含主机调度与等待校验锁。它不包含设备 USB/硬件队列，也不是线上延迟。负时间单独报告并禁止 pass，不夹成零。原生 worker 的 enqueue→worker_started 驻留仍通过主机计时 host timing 直方图提供，未提供深度的后端不能推断其硬件队列高水位。

QueueSample 保存 channel、ordinal、received_ns、processed_ns 和 depth，独立复算检查声明、角色、时间与序号边界并重新构建全部桶、分位数及高水位。完整 RX 原始样本模式还核对队列采样覆盖数。未开启完整原始样本时，只证明持久化采样的分布和累计报告一致，不宣称重捕获所有 RX。

滑动叶子流的所有证据使用 TrackingRecord 放进同一个按入队顺序持久化的 metrics 流；多流再包外层 FlowRecord。TrackingAdvance 必须有精确结算的 TX 前缀；发送结果不能在缺少推进记录时越过窗口，防止删除中间淘汰记录后继续复算。完整 RX 模式重建环形位图、每阶段计数、淘汰缺失和迟到；运行结束后的 RX/推进记录拒绝。窗口冻结计数和队列采样计数不能回退。

没有完整 RX 样本时，RX 结论仍是在线累计报告；离线验证只检查窗口元数据、推进顺序、发送集合、队列采样及累计结论的守恒，不扩大证明范围。恢复仅扫描已有证据和有效前缀，损坏或缺尾清除完整性及通过结论，不打开设备、不重新发送。新可选采样、窗口推进和提交区间刷新一并计入每秒 2000 条的记录预算，以及磁盘、分段和多流总预算。

JSON 的浮点秒数启用无损往返解析，修复真实时钟下自适应子报告可能因一个浮点精度单位而与 FlowEnd 不相等的问题；子报告仍严格相等，不放宽为近似比较。新增精度回归验证原始浮点位模式。

Web 提供 exact/sliding、容量和队列采样间隔输入；报告对叶子流、自适应子阶段和多流分别展示窗口边界、冻结缺失、迟到及采样高水位/驻留 p99。完整报告 JSON 保留所有桶与计数，可下载独立复算。

### 首次交付时的吞吐未通过记录（历史保留）

功能验证通过不等于此时的主机吞吐达标。保留原有门槛并显式运行两项虚拟基准：

- 40,000 帧快速路径的首次结果为 **25,225 frames/s**，低于既有 **40,000 frames/s** 门槛；后续同代码为 12,740 / 13,861 frames/s，均未通过。最后一次进程总墙钟 3.37 秒、user+sys CPU 约 0.51 秒，说明测试大部分时间未获得 CPU。只读检查同时观察到后台虚拟机约 222% CPU、文件事件服务约 103% CPU，以及多个编译进程；系统未报告温控告警。主机存在显著竞争，仍不能把折算的 CPU 吞吐当作门禁通过。
- 带记录的 10,000 fps 调度基准同时跑 exact 与 sliding+queues：首次分别 submitted **3,994 / 2,639**、skipped **6,006 / 7,361**；每个模式 peer RX 均等于 submitted、missing_submitted=0、无 RX lag，证据完整，报告正确给出 **fail**。证据守恒检查通过，目标吞吐未达成。

该功能软件功能已交付，**吞吐验收仍需在空闲主机复测**；没有修改 20,000 fps 预算、两倍余量门槛或严格默认判据来掩盖失败。后台其他工作未被暂停或终止。实际 24 小时测试、真实硬件、USB 拔插/睡眠和外部 SSH 均未执行；没有向真实 CAN 设备发送帧。

## 吞吐复查与优化（2026-11-08）

结论：存在可以消除的 CPU 开销，但此前从约 8 万跌至 1–2 万 frames/s 的现象不能用固定的代码回退解释。同一未优化版本本轮即可达到 85,711 frames/s；在交错试验中，同一基线二进制又从约 24 万跌至 39,273 frames/s。主机运行条件有显著影响。**最终开启队列监控的 exact/sliding 各三轮均达到目标；包含其他配置与快速路径的整体重复门禁仍未全部通过。** 不把局部通过替代完整验收。

### 对照方法与证据

- 保持原始快速路径 **40,000 frames/s**（20,000 预算的两倍余量）、记录路径 **10,000 个计划槽位 / 10,000 fps / 零跳过 / peer RX=10,000 / verdict=pass / recovery=verified**。没有调整调度迟到阈值、量化窗口、发送授权或优先级。
- 修复基准本身的一个缺口：旧记录测试只检查 submitted+skipped 守恒和无未报告 RX 丢失，报告 fail 时测试仍可返回成功。现在全部模式执行完、清理完后统一检查吞吐条件，失败必须非零退出。原测试名称保留，严格检查增加，没有降低产品门槛。
- 比较 exact、exact+queues、sliding、sliding+queues，队列间隔统一为 100，窗口容量 4096，原始采样间隔统一为 20。这样不再把“精确不监控”和“窗口带监控”的成本混成一个因素。报告增加调度最大迟到和观察队列高水位诊断。
- 预先编译并复制优化前后的二进制，在测量期间不编译；三轮交错、隔轮反转版本顺序，所有失败也保留。baseline 是**本轮优化前的滑动窗口**，不是可重建的自适应负载源码版本，不据此宣称精确测得自适应负载到滑动窗口的全部差异。
- 新增 [stress-throughput.py](../scripts/stress-throughput.py)：固定运行虚拟测试，保存二进制 SHA-256、退出状态、墙钟与进程 CPU 时间、上下文切换、逐模式结果和完整输出；缺失模式或未达到原门槛均返回失败。CPU 时间只用于解释成本，不折算成替代墙钟的通过结果。记录型压测本来会主动按速率等待，因此不能单靠其 CPU/墙钟比推断被抢占。
- [初始优化对照](benchmarks/stress-batch6-paired-initial.json) 和 [最终对照原始记录](benchmarks/stress-batch6-paired-final.json) 各包含 18 次进程执行。两份 current 对应不同优化阶段，最终结论使用 final，不能混合挑选最好样本。

复现时，先用相同配置构建 `cargo test -p canharbor-stress --lib --all-features --locked --no-run` 和 `cargo test -p canharbor-server --test stress --all-features --locked --no-run`，从构建输出取得测试可执行文件。沿用本仓库验证环境：`CARGO_INCREMENTAL=0 CARGO_PROFILE_DEV_DEBUG=0 CARGO_PROFILE_TEST_DEBUG=0`，编译并发限制为 `CARGO_BUILD_JOBS=2`；编译必须结束后再测量。将 stress 单元测试二进制同时传给脚本 `--lane` 和 `--verifier`，server stress 测试二进制传给 `--recorded`，指定 `--rounds 3 --output <结果.json>`。可另传三个 `--baseline-*` 二进制参数做交错对照。脚本不会重试到成功、改变系统优先级或终止其他应用。

### 代码优化与语义保护

1. exact 保留完整 RX 位图，在结束时用位图重建阶段计数，移除原来无用的逐帧阶段扫描和阶段辅助数组。
2. sliding 的常见单阶段流直接累加，多阶段由线性查找改为对已编译、有序阶段起点二分定位。容量、淘汰、迟到和 TX 精确集合规则不变。
3. 未开启队列监控时，先检查选项，跳过新增的 eligible RX 关联判断。
4. 未开启 host timing 时，跳过仅为计时匹配服务的额外 payload decode。**接收校验器仍完整执行 CRC/模式校验**；启用计时、RTT 与 Classic checkpoint 的既有校验流程保留。没有修改控制面锁、租约、停止门或任何发送许可检查。

### 最终三轮结果与限制

在每种模式处理 640,000 个 Classic 帧的纯校验诊断中，64 个编译阶段的进程 CPU 时间中位数：exact 从 **0.392019 秒降到 0.307187 秒（约 21.6%）**，sliding 从 **0.503507 秒降到 0.433683 秒（约 13.9%）**。单阶段分别变化约 −2.1% / −1.2%。这只是该机三轮的样本中位数，CPU 频率、核心分配与后台工作也会影响 CPU 时间，不作为统计显著性或其他主机性能承诺。纯校验诊断没有发送到任何后端，也不能替代两项真实时钟虚拟门禁。

- 快速路径：baseline 三轮 **241,151 / 231,949 / 39,273 fps**；最终版本 **239,465 / 237,902 / 30,012 fps**。前两轮两版均通过，末轮两版均失败。末轮进程 CPU/墙钟分别约 **0.469/1.116 秒**和 **0.379/1.416 秒**：计算 CPU 更少也可能墙钟更慢，不能把墙钟下降简单当作代码计算变慢。
- 最终 exact、不监控：submitted **9,801 / 10,000 / 9,832**，skipped **199 / 0 / 168**。
- 最终 sliding、不监控：submitted **10,000 / 10,000 / 9,880**，skipped **0 / 0 / 120**。
- 最终 exact+queues 和 sliding+queues：各三轮都是 **submitted=peer RX=10,000、skipped=0、verdict=pass、recovery=verified**。但这不意味着采样会提高吞吐；不同时间段的调度竞争和固定模式顺序仍是干扰因素。
- 最终版本中有跳过的样本最大 dispatch lateness 为 **10.844–17.962 ms**，零跳过样本均低于原来的 10 ms 跳过界限。所有模式仍满足接收/提交守恒、无未报告 RX 丢失和完整证据。失败被保留为 fail，基准返回非零。

本轮只读观察到后台虚拟机、Go 测试/静态检查和文件事件服务等并发占用，未报告系统温控告警；没有暂停或终止其他工作。CPU/墙钟差还包含异步等待，不能仅靠它精确分摊每一项原因。证据支持“主机调度/运行条件主导大幅波动，新增的无用 CPU 工作可以优化”，**不支持宣称所有代码性能差异已被完全排除**。正式吞吐稳定性验收仍需要可控、空闲主机重复满足全部配置门禁。
